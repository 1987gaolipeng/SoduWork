# 智能联动：意图、成果、行动与回执

即用承载业务操作与结果，SoduWork 提供模型、会话和执行能力。设计应让用户提出意图，由 AI 理解、规划或处理，结果直接成为页面可用的业务对象，用户可继续修改、确认和追踪；避免只做传统管理表单或把结果留在聊天里让用户复制粘贴。确定性搜索、复制、校验和实时交互仍直接执行。

## 开发时必须落实到应用内技能与页面

凡涉及 AI 处理结果回到页面的即用，开发者必须同时实现技能端和页面端，并将两端联动作为功能交付条件。仅在本开发插件中描述宿主能力、只写技能或只画页面，均不算完成。

- **应用内技能端**：将联动要求写入所开发即用的 `instructions` / 随包业务技能，使应用运行时实际加载。明确接收的意图与目标、请求关联、结构化成果格式、授权工具、写回位置、读回确认、失败回执及需要用户确认的动作；不得只输出聊天说明或要求用户复制到页面。
- **应用页面端**：实现与技能一致的请求/成果格式及存储或 API 对接，提交上下文，接收或补读结果，校验后展示并回填；按业务实现通知后应用或直接更新，需要执行时支持确认当前版本并追踪真实回执。不能只留一个“交给 SoduWork”按钮和刷新占位。
- **共同契约**：两端使用一致的请求ID、目标ID、类型/结构、版本和状态含义；所需声明、技能资源、工具连接和页面处理器一起交付。简单 `ai.generate` 路径使用随包聚焦提示词与页面结果解析/处理配套，无需强行增加 MCP 或会话；确定性功能无需增加无关AI流程。
- **验收条件**：实际验证“页面提出需求→应用内技能处理→成果回填页面→应用或确认→查看真实结果”。任一必要端缺失、仅聊天回复或仅刷新提示，都不得交付为已完成联动；缺运行条件明确记录未验证。

## 声明实际支持的能力

开发前说明：核心意图、AI负责什么、结果落在哪里、页面怎样更新、什么动作需确认、如何查看最终结果。按真实 SDK 在 `source.bridge.capabilities` 声明所需能力；声明不代表接口已经实现或任务已经成功。

| 业务需要 | 当前可用路径 | 边界 |
| --- | --- | --- |
| 页面内生成/改写/分类/短步骤建议 | `soduWorkApp.ai.generate`；声明 `ai.generate` | 单次文字生成，无历史、Agent规划器或工具；结果由页面校验、回显和按需保存 |
| 多步骤规划、查资料、调用工具、执行工作 | `soduWorkApp.chat.send`；声明 `conversation.send`，控制对话栏另声明 `composer.control` | 使用当前即用会话、随包业务技能和本轮授权能力；发送受理不是完成 |
| 页面与 AI 共用业务成果 | 页面 `data.get/list/batch`，技能通过宿主 `soduwork-jiyong` 的 `data_get/list/batch` | 按 host-sdk.md 与 cloud-data.md 声明存储位置、集合、data.read/write、mcp.connect 与 MCP；同源存储、revision 合并及读回 |
| 在线业务的成果/进度/消息 | 现有业务 API/MCP + 页面读取 | 业务端保存并校验权限；不用本机数据冒充跨机器同步 |
| 页面获知数据可能变化 | `events.onRefresh/onTurnSettled` + 加载/聚焦补读 | 轮次结束信号，无业务正文/请求ID，不是完成通知；两方法是同一信号，选一个订阅 |
| 宿主通知、对话或资料变化 | `events.onDataChanged` + 对应读取接口 | 仅 identity/notifications/conversations/library 主题；不是即用自有集合的变更推送 |
| 定时或持续工作 | `automation.create` + 现有 Hub/Runner | 不另建调度；创建计划不代表执行完成；页面关闭与执行设备离线分别处理 |

当前没有宿主通用 `send_app_message/onMessage`，没有页面任意 Shell/Node/IPC 执行接口，也没有单独的“轻量规划”SDK。不要把建议的业务 type、字段或处理器写成宿主内置接口。详细方法、参数和权限以随包 SDK 为准。

## 简单 AI 与复杂执行的分工

- 输入已齐全、一次推理能完成的语义任务，优先在即用内部调用 `ai.generate`，随包提供聚焦技能提示词，结果直接回到当前页面；短方案/命令草稿也可按此处理，但生成不等于执行。只传必要素材；需要结构化结果时约定 JSON 并在页面解析、校验字段与业务约束，当前接口返回 text，不保证结构化输出。限制与重试见 [fast-ai.md](fast-ai.md)。
- 需要读取上下文、使用工具、复杂规划、跨步骤执行或持续追踪时，交给 SoduWork 当前即用会话 `chat.send`；技能约定工具、目标对象、写回方式和完成证据。不要额外建设平行聊天/Agent状态体系，也不要为了简单改写强制展开聊天。

## 结果回到页面的闭环

1. 页面保存业务请求及稳定 `requestId`，携带目标对象、输入版本和必要上下文；不要假设 `chat.send` 的传输编号会自动传给工具，业务正文/记录中也应明确关联编号。
2. 技能读取真实业务记录，通过授权 MCP 写入结构化成果或消息，并读回核对。纯本机即用优先复用宿主声明集合，不为通知单独搭服务；在线即用复用自己的业务存储。
3. 页面在加载、聚焦和轮次结束时重新读取权威记录。长执行若需中途进度，使用已有业务推送或仅对可见的待处理请求做有界补读；轮次结束事件不提供实时执行流，不能用虚构进度代替。卸载解除订阅，隐藏时停止页面轮询，重开补读。
4. 按业务选择交互：低风险且可撤销的成果可直接合并显示；需要审阅、存在冲突或会触发实际操作时，在即用内部显示“方案已就绪/待确认”，点击查看差异并应用。无须每次弹消息，也不能只在右侧对话说完成。
5. 请求编号关联已有任务/运行回执；去重、校验类型/字段、当前账号/对象/版本，防止旧结果覆盖新编辑。状态来自真实回执，区分已受理、方案就绪、待确认、执行中及真实终态；复用宿主执行状态，页面只保存业务关联和展示。未拿到证据保持待确认，失败保留输入。

业务记录可按需包含 `requestId/type/targetId/baseRevision/payload/resultRef`；这些是前端与技能共同约定的业务字段，不是 SDK 参数。消息与业务成果可分别存储，以消息ID去重并记录已读/已应用；消息送达不等于成果已应用，更不等于执行成功。只分发到预先实现的业务处理器，不执行模型给出的任意 JS/HTML。

## 两类建议

- **流程画布**：页面提交当前流程和修订号，AI 将规划保存为节点/连线或可校验的变更集；页面提示“方案已就绪，更新画布”，也可按需求直接更新低风险草稿。应用前校验节点/连线引用与版本，保留用户新编辑，支持撤销/版本回看；没有实际执行时只显示规划完成。
- **Shell 工具**：AI 将命令草案直接回填到即用，含命令、Shell类型、工作目录、执行目标和影响说明；建议通过即用内部待确认消息呈现。用户可检查/修改，确认当前准确版本后，才交现有授权会话/Runner/业务执行器执行；生成阶段技能不得顺手执行。不能用“确认”按钮直接调用不存在的页面Shell接口，也不能把确认文案当作执行授权凭据。执行端校验授权与确认范围，变更命令/目标后重新确认。用真实执行ID追踪运行、stdout/stderr、退出码及业务结果；断线显示未知并核对原执行，禁止自动重发有副作用的命令。

## 验收

覆盖意图→AI→结构化写回→页面补读→消息/直接更新→确认（如需）→执行回执→关闭重开回看；补测重复通知、失败/取消、超时未知、迟到结果、并发编辑、切号和缺权限。静态脚手架默认只有发送与刷新占位，必须补齐本业务闭环后才称为智能即用；夹具不证明真实模型或真实命令已执行。
