# 业务梳理与验收

用当前已有资料填清以下问题，不必把它们逐条重新问用户。

| 内容 | 应沉淀什么 |
| --- | --- |
| 使用场景 | 谁会使用、什么请求触发、哪些相似请求不应触发 |
| 输入 | 必需文件、字段、图片、历史上下文及缺失时如何补充 |
| 规则 | 来源、优先级、可配置参数、不能自行猜测的业务口径 |
| 执行 | 有顺序的动作、工具依赖、失败退出或人工确认条件 |
| 输出 | 文件类型、结构、示例、命名和验收标准 |
| 权限 | 只读/写入/外发边界；敏感配置留给宿主连接 |

避免写成泛泛角色设定。把用户实际业务规则写成可操作步骤，不要收录整段聊天或含个人信息的原始文件。保留必要背景和脱敏样例即可。

## 调整已有 Skill

先说明原包的触发条件、资源与行为，再实施用户要求的最小修改。保留无关资源、许可、宿主配置和相对路径。生成文件级变更清单，并解释行为变化。若要删除文件、改变权限或更换 Skill 名称，先得到明确确认。

## 验收记录

1. 正常输入：给出输入样例、预期文件及关键内容，并实际检查。
2. 缺失输入：应明确列出待补信息，不编造数据或继续外发。
3. 边界/异常：验证规则冲突、空数据、坏格式或重复操作时的处理。

脚本用临时脱敏数据测试，记录命令、退出状态和实际输出。只完成手工推演时写“推演”，不要写“运行通过”。外部宿主、模型或业务系统未测试时分别列出。不得自动发送通知、写生产数据或安装未知依赖来凑测试通过。
