# SoduWork 桌面客户端

**简体中文** · [English](README.md) · [开发指南](../docs/development.md#桌面客户端)

命令示例中的 `sh start.sh` 适用于 macOS/Linux；Windows PowerShell 使用 `.\start.cmd`，命令提示符使用 `start.cmd`，参数相同。独立 Python 工具示例使用 `python3`；Windows 使用 `py`，已激活虚拟环境时使用 `python`。

当前工作区使用 Electron 与原生 HTML/CSS/JavaScript；管理端的 React 构建不参与桌面渲染。

## 构建时指定默认 Hub

常规构建仍默认连接 `https://service.soduwork.ai`。为其他部署打包时，在运行
`npm run build`、`npm run build:linux` 或 `npm run build:mac` 时设置
`SODUWORK_DEFAULT_HUB_URL`。地址必须是 HTTP(S) origin，不包含凭据、路径、查询参数或片段。
例如 Linux：

```sh
SODUWORK_DEFAULT_HUB_URL=https://hub.example.com npm run build:linux
```

不设置或留空时保留原默认地址。地址在签名前写入安装包，运行时环境变量不能覆盖；
用户已保存的服务选择仍优先。应用名称、版本、安装身份、数据目录、更新信任和安装包文件名保持一致。

手动运行 Actions 的 **On-demand client packages**，填写 `default_hub_url` 和
`artifact_label`（如 `cn`），选择包含目标版本及这些构建工具的受保护分支。
该版本必须已有正式 Release；每个平台的安装包复用经校验的正式发布说明。
流程执行质量检查、签名和原生安装验收，产物按标签区分，在 Actions 保留 30 天；
不创建 GitHub Release，也不部署 Hub。每份下载附有 `client-packages.json`，记录
默认地址、源码提交、构建编号和文件摘要。不同环境的下载应放入独立目录。
部署时将原安装包连同更新签名清单上传到目标 Hub，详见
[发布流程](../.github/RELEASE.md#on-demand-client-packages)。

本机资料库导入时保留文件扩展名，并为重复文件的编号预留长度。旧版本保存的文件若存在重名、无效名称或疑似截断，会显示“请核对文件名”；提示不代表文件内容损坏。在资料菜单选择“修复文件名”，确认包含正确扩展名的完整名称，即可替换错误后缀或补回缺失后缀，并保留资料 ID、内容、来源和所在文件夹。普通“重命名”仍保留原扩展名。所有本机文件都可使用修复入口，包括已被手动改过名称的旧条目；远程存储不提供此操作。

旧数据不一定保留原始扩展名，客户端不会猜测后缀或自动改名。请根据原文件或来源核对后确认；不知道正确名称时，可先导出副本进行检查。旧重名条目的内容各自保留，可分别修复为不同名称。修复名称不会转换文件格式，也不会绕过程序文件的系统打开限制。

原生文件交付保留 Unicode 文件名的原始形式与文件字节，包括成果包内的相对链接。桌面与 Hub 需要一起更新，才能接收分解形式的 Unicode 名称；规范化后等价或大小写冲突的路径会被拒绝，不会合并覆盖。Pi 已完成轮次的变更记录可在现有扫描限制内找回保留旧修改时间的本轮文件，不纳入无关历史文件；冻结文件前会核对记录中的内容哈希。明确声明文件路径的交付契约在没有采集到成果或推断扫描不完整时报告交付未完成；纯文本及仅声明成果类型的契约沿用原有行为。手动提交模式的已完成轮次显示仍待提交验收。传输继续复用按账号隔离的持久化回执队列。

新建本机需求执行将提交选择与实际提交方式分开保存。默认选项可在本轮正式成果校验通过后提交验收，不再要求预先声明输出契约；明确手动以及无法确认来源的历史手动策略保持不变。明确选择默认选项时需更新后的 Hub 确认。独立聊天中的 JSON 成果可与 Markdown 一样采集，配置、凭证、隐藏目录及过程文件仍不参与自动推断；工程目录保留有界成果规则，显式清单仍优先。

完成轮次的文件采集前，现有持久化队列会记录绑定本轮的待采集回执。重启后可看到采集中断，不会从已变化的工作区重建结果或重新运行模型。采集完成后按冻结字节补发，不重复生成验收请求。需求详情区分待同步、手动提交、交付与验收人阻塞。在首次持久化写入前发生的磁盘错误只能在本机报告，不能保证重启恢复。验收人不可用时需恢复创建人账号，归属缺失则由管理员核实；执行权限不等于验收权限。

从完成通知打开需求时，即使尚未访问需求池，也会刷新审批列表。非仓库变更流程的本机文件交付先提交验收记录，再由现有通知队列发送通知；通知传输失败重试时保留已提交的验收记录。同一轮执行恢复后，可将先前仅留作未完成过程证据的文件正式交付，兼容旧客户端回执；显式手动提交仍保持手动。验收导航区分普通打开与验收意图，旧审批不会清除当前验收上下文。这些交付与通知修复需要桌面和 Hub 一起更新。

排查需求执行后未进入验收时，先退出已有桌面，在仓库根目录的 PowerShell 中开启可选的本地诊断记录，再启动源码桌面：

```powershell
$env:SODUWORK_REQUIREMENT_DIAGNOSTICS_DIR = Join-Path $env:TEMP ('soduwork-requirement-diagnostics-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
Write-Output $env:SODUWORK_REQUIREMENT_DIAGNOSTICS_DIR
.\start.cmd --desktop
```

使用合成需求，保持与出问题时相同的执行入口、模型和提交选项。执行结束后等待 30 秒，再打开一次需求详情，保留打印目录中的全部 `requirement-*.jsonl` 文件及大致复现时间。这些文件就是诊断导出，不会自动上传。确认文件包含 `diagnostics.startup`，避免误用仍在运行的旧桌面。下次正常启动前执行 `Remove-Item Env:SODUWORK_REQUIREMENT_DIAGNOSTICS_DIR` 关闭诊断；该变量不会更改已配置的 Hub 或账号。

诊断记录覆盖界面收到的需求响应和事件、原生会话的需求绑定、选择及生效的提交方式、成果捕获结果、交付响应和回执重试。标识及服务、账号关联键均使用哈希；不记录提示词、标题、文件名、文件内容、令牌或原始错误。每个进程达到 5 MiB 后以 `diagnostics.limit` 标记停止记录，此时需重新启动一次诊断。诊断写入失败不会中断执行。启动记录包含可获得的本地源码指纹和 Git 版本，实际 Hub 版本明确标为未知。界面记录只能证明收到的状态，不能证明具体控件已经绘制。提交、验收策略和业务数据保持原有行为。

切换底座时，会话保留已登记成果的可验证索引。历史图片、文档和媒体在后续切换或重新打开后仍可访问，但不会自动变成本轮交付；当前底座的已完成回复可以明确再次交付历史成果。读取时重新校验工作区和文件版本；文件变化后须由当前可信索引重新确认，不能借旧历史记录继续读取。历史插件包及其资源会重新检查后才显示可安装状态。缺少可信索引的旧切换记录不会根据消息中的任意链接重建。预览读取若被并发切换中断，最多对同一读取重新授权一次；账号变化、权限失败和文件操作不自动重试。图片加载及失败卡片在窄窗口中仍保持可读布局。可运行 `node e2e/chat-media-error-layout.cjs /absolute/evidence/directory`，用合成图片在 Electron 中验证加载、失败和重试后的图片卡片。

普通新对话使用独立工作目录，不自动继承上一会话目录或最近选择的目录；显式选择的项目文件夹仍可共享。个人记忆不再自动积累底座身份、模型自我介绍和知识截止日期，注入本地历史记忆时也会过滤这些内容。“我的记忆”默认展示 Markdown 排版，可展开“编辑 Markdown”修改源码。已有会话的历史和工作目录保持不变。

在显式选择的工作目录或项目目录中新建本地普通对话或目标，并成功发送首条消息后，桌面会成对记住实际使用的底座和模型。下次在该目录新建会话，或在新草稿中选择该目录时，两者均可用才会恢复选中。偏好按当前 Hub、账号和设备隔离，云端执行沿用原有选择流程，临时工作区不共享目录偏好。如果保存的底座或模型不可用，需要明确选择可用组合；自动回退不会覆盖原组合，未发送草稿中的修改也不会替换上次使用的选择。Codex 账号底座未能确认具体模型时，不保存目录偏好。

桌面 Markdown 将单个波浪号视为普通字符，同一段落中的 `3~5`、`7~14` 等区间会保留分隔符。删除线使用 `~~文字~~`。共用的 `core/markdown.js` 配置覆盖会话历史、流式回复、朗读文本提取及 Markdown 预览，不修改已保存的原始文本。

双星号加粗也支持紧邻中日韩文字的标点，例如 `**注意：**这里` 和 `这是**“重点”**内容`。行内代码、代码块、转义星号和链接地址保留原有 Markdown 含义。

## 模块边界

| 位置 | 职责 |
| --- | --- |
| `main.js`、`main/` | 应用启动、原生窗口、设备身份、更新、文件及执行底座；覆盖窗生命周期在 `main/desktop-overlay.cjs` |
| `preload.js` | 受限的渲染端 IPC 接口；不向页面开放通用 Node 权限 |
| `desk.html`、`desk-boot.js` | 主工作区的资源装载与启动 |
| `index.html` | 透明桌宠及快捷工具覆盖窗 |
| `core/` | 客户端状态、同步、语言及共享基础能力 |
| `components/requirements/` | 需求池、单一需求抽屉、派活生命周期及共享表单字段 |
| `components/` 其它目录 | 对话、AI 团队、插件等界面模块；共用执行选择器保留在 `panels/` |
| `theme/`、`assets/`、`vendor/` | 主题、素材及带许可的随附依赖 |
| `tests/`、`e2e/` | 单元/契约检查与 Electron 场景验证；不随产品安装 |
| `scripts/`、`build/` | 运行时准备、打包与原生安装支持 |
| `runner/`、`dist/`、`.runtime/` | 生成的 Runner、发行包和随附运行时；不作为源码维护 |

普通对话、需求执行与目标使用同一会话链路：`panels-chat` → `conversationSession` → 主进程会话 IPC → `agent-runtime` → Pi 或 Runner。AI 团队点击工作打开对应会话；需求抽屉按需展开共享 TaskTrace。桌面竖条直接进入需求池，不保留旧任务看板、旧详情聊天框或独立 AI 工位会话。旧 `detail` 链接继续定位同一条需求，不新增数据记录。

普通会话在所有底座上保持对话模式，即使消息要求分阶段实施或继续完成工作，也不会自动进入目标循环。目标循环必须通过明确的目标配置启动，桌面不根据消息措辞推断持久目标模式。已经配置的目标继续保留暂停、继续、停止和恢复控制。

历史列表刷新时，会为同一账号的同一会话保留已观察到的全部底座执行来源，包括持久索引尚未同步最新运行状态的情况。尚未发送的底座选择不算使用记录。运行 `node e2e/history-goal-intent.cjs /absolute/evidence/directory` 可在真实 Electron 中验证侧栏和目标控件，使用模拟历史和 Runner 回执，不调用真实模型。

Runner 插件草稿检查无法读取文件时，对话会提示失败并结束执行中状态。已有文件保留，依赖前一项的队列等待用户明确恢复；最终检查失败不会重放已完成的模型请求。检查期间取消或切换权限时，保留用户的新控制状态。

选择内置「插件开发助手」后，当前已授权轮次明确进入插件制作：消息描述的是可复用插件的行为，每次使用时变化的参数应定义为插件输入，不直接执行一次性业务任务。仍可询问制作插件必需的信息。生成的插件包通过现有草稿检查后，对话才提供「检查并安装」入口，安装仍需用户确认。普通对话和其他插件保持原有行为。

需求创建人和执行人为同一人时，执行继续使用原会话。用户明确选择的底座或模型通过正常的原生选择事务生效，会话 ID 和历史保持不变；验收也复用原执行会话。Pi 和其他底座遵循相同规则，只有主进程明确确认原归档不存在时才新建会话。暂时读取失败、无权访问或底座切换尚未确认时，保留原会话并停止提交。

三端结构、派活规则和保留的兼容边界见 [当前需求工程结构](../docs/release-scope.md)。

渲染脚本按 HTML 中的顺序共享作用域。拆分时同时核对资源引用、顶层声明、调用顺序和 Electron 加载；单独语法检查不足以证明页面可用。

对话中的自动化草稿支持“五分钟后”等相对时间，以消息提交时刻计算执行时间，后续只补充任务内容时保留原时刻。缺失、无效或有歧义的时间需要补充确认，不再默认设置为每天 18:00；任务内容不明确时也保持草稿。用户可以取消创建、继续通过对话完善同一卡片，或返回普通聊天。创建后，明确的修改请求先生成待确认的变更，再按原自动化 ID 保存；取消修改保留已保存配置。停用会停止后续自动触发，关闭卡片只收起界面。运行 `node e2e/automation-sheet-layout.cjs /absolute/evidence/directory`，通过模拟解析和计划 API 验证隔离 Electron 中的表单与对话路由。

未确认的草稿支持连续多次修改时间。“修改为10分钟以后”等明确的纯时间消息在本地更新同一份草稿，支持“后、之后、以后、过后”，模型解析不可用时仍能生效。每次相对时间都以该条消息提交时刻为基准，在异步访问检查前记录；标题、执行说明和完成标准中的执行时间标注同步更新，其他业务时长保持不变。恢复卡片保留最新执行时刻，用户确认前不会创建任务。

本地草稿解析遵循模型检测得到的输出 Token 参数和已配置的输出预算，并受上下文窗口限制。未配置输出预算时使用统一的 16,384 Token 默认值，不再固定限制为 1,024 Token；原生调用明确指定的较小预算仍然生效。普通插件 AI 调用保留独立限额。输出截断（包括推理耗尽预算但尚未生成正文）会明确提示输出上限，不会生成不完整草稿。模型服务失败时保留安全的 HTTP 状态，分别提示凭据、权限、服务地址或模型名称、参数兼容、限流及服务故障；不暴露原始服务响应，也不会自动重试请求。补充解析失败时保留具体原因和原草稿。Runner 就绪只表示执行前置条件已满足，不代表模型解析成功。本地需求表单把原文、附件和补充要求作为用户输入，只从模型最终返回的单个 JSON 对象提取草稿。如果模型只返回网页实现或不完整的答案，表单会保留原文供编辑。

在同一台电脑、同一系统用户和同一 Hub 下切换 SoduWork 账号，两个账号都能查看并继续普通本地聊天。续聊使用当前账号的执行身份。带有需求、验收、自动化表单或私有记忆记录的聊天，以及云端会话、下载或导入的副本，仍按账号授权。旧版本只保存了部分记忆使用记录。归属未知的归档可明确导入为独立的只读副本。归档、删除、远程读取和迁移继续校验原账号权限。

新建或继续普通本地聊天时，客户端不会自动读取或更新个人、组织或工作记忆。如需使用私有记忆，可在新建聊天时选中该记忆。使用过私有记忆的会话由使用它的账号查看和继续。

首条消息发送前可以选择「本地」或「云端」，默认本地。本机会话及其目录归属当前电脑，使用在线模型也保留这个归属。云端会话由 Hub 提供给同一账号已授权的设备查看和继续。已有本地归档、下载记录和旧版待处理数据继续保留。

普通本地聊天进行时，桌面端会持续保存用户输入和助手回复中可见的文字，写入本机 `conversation-replicas/history.sqlite` 的 `conversation_transcript` 表。切换模型或底座后仍沿用同一会话 ID。升级时会在原数据库中新增此表并保留已有历史。即使后来清理了原生档案，重启客户端后仍可查看已经写入的文字。

桌面端还会从可读取的原生档案回填消息和工具回执，用于核验能否恢复执行或迁移。打开时会检查会话归属，并区分档案缺失与临时读取失败。若只剩已保存的文字，仍可查看。在原会话下开启新的执行段，需要有可核验的完整历史，并确认历史工具操作都已结束。如果升级前所有本地副本中的正文或文件都已被清理，仅凭侧栏标题无法找回。

打开已保存的普通本地聊天时，会先显示消息和工具记录。要继续聊天，可选择当前账号可用的底座和模型后发送消息，新一轮沿用原会话 ID 和此前的对话。如果有工具缺少最终结果，仍能查看已保存的内容；恢复执行或迁移需要先核实该结果。对于旧版 Codex Harness 会话，桌面可用本机 Codex 存档中同一次调用的回执核实图片读取结果。如果之后清理了 Codex 存档，只要仍能核实是同一会话且 Runner 执行记录完整、未变，桌面就能继续使用本机已验证的回执。仍有工具结果无法核实时，输入框保持可见并提示只读。

对于旧版 Qwen 会话，桌面还可以通过本机 Qwen 回执确认某次文件写入在开始前已取消。继续聊天时会保留该取消状态。

如果已保存的 Pi 原生档案后来被截短或改写，桌面会保留上一次核验完整的本机副本供查看，并暂停续聊和迁移。恢复原档后可以重新核验，原档末尾正常追加的记录也会保留。

会话项目同步只共享已验证的云端成员及其项目名称，只有本地会话的项目保留在电脑上。混合项目的云端成员变化或远程项目被删除时，保留本机成员和文件夹；原生会话 ID、编码后的设备引用、本地标题和工作区路径不会作为项目成员上传。

历史回复中的截图相册会按相对路径匹配会话文件索引。文件缺失或有多个匹配项时，对应位置会提示无法预览。经核验的主产物显示在关联回复下方。索引只记录了所属会话时，主产物列在「会话成果」中。

工作表单对话在执行前即显示已保存的底座图标，侧栏提示为“已选底座”。切换选择和重新打开后保持正确图标，并与实际执行记录分别处理；没有保存选择的旧草稿不根据存档格式猜测底座。运行 `node e2e/workspace-runtime-label.cjs /absolute/evidence/directory`，可在隔离 Electron 中验证草稿更新、历史恢复和窄侧栏布局。

浏览器同时支持 IndexedDB 与 Web Locks 时，远端通知历史和回执标记使用账号隔离的事务存储；本地提醒继续使用既有 localStorage 缓存。迁移只有在持久化提交成功后才清理旧快照，写入失败会保留旧快照以便重试。不具备这些浏览器能力的环境保持既有缓存行为。

同事消息的送达和已读回执保留原附件列表，发送人也可以查看。打开附件时，为当前登录的发送人或收件人重新获取已授权文件信息。以通用二进制类型发送的受支持文本、位图和 PDF 使用现有受限原生预览；文本按原文显示，不扩大系统打开可执行文件的允许范围。接收或打开文件不会自动保存到资料库。

需求的交付区域支持通过原生保存框，将单条验收摘要导出为 Markdown。导出需要执行记录查看权限和已经固定的交付版本。摘要读取一致快照，区分当前需求正文与已记录的验收标准；缺失的验证结果或运行归属明确标为未记录。导出不会通过验收或修改需求。

没有交付清单时，Pi 或 Runner 已完成回复中明确链接的最终文件用于选择本轮需求交付。修改过的中间稿保留在工作目录和会话历史中，不混入验收输入；多个明确链接的成果及其必需资源仍会保留。思考、工具参数、最后一次工具调用前的正文、内部进度消息和未完成回复不用于选择最终文件。显式交付清单仍遵循完整集合与 replaces 替换语义，不会仅凭文件名中的版本后缀替换旧文件。

在 `client/` 中运行 `node e2e/run-requirements-isolated.cjs /absolute/evidence/directory /path/to/test/python requirements-rework-renamed`，可验证普通退回修改经过生产捕获、隔离 Hub、验收输入和 Electron 需求详情的完整链路。Python 环境需要后端测试依赖。文件生成由确定性夹具完成，不调用真实模型。

同一区域提供默认折叠的派发说明。新桌面派发按每次获准进入队列的执行轮次，保存用户明确填写的补充内容、选择的提交方式及当次实际提交方式，执行失败也保留记录。本机、Runner 和工作流共用这一回执链路。同轮重试不能覆盖说明，后续轮次单独保存；只有原有执行记录查看权限的用户可以读取。旧客户端和缺少明确快照的历史条目显示为未记录，不从聊天内容、截断的旧上下文或当前路由推测补齐。

在会话中分析和自动验收会带入已保存的需求、派发补充说明与验收退回意见。业务要求冲突时按最新记录时间处理，不冲突的要求继续有效；时间缺失或相同且无法判断先后时，明确提示需要确认，不推测优先级。生成的草稿再次发送不会改变历史内容的时间，本次验收人新增意见单独携带；准备后历史记录变化会使本轮验收失效。固定交付版本、验收标准编号和审批权限仍由原契约控制。客户端与 Hub 均需升级才能加载完整历史，旧服务会明确提示记录缺失；历史过长时停止并提示，不静默截断。

Runner 会话区分排队、等待执行环境启动和实际执行。队列显示所在序号与等待时长，执行时间从原生进程的启动回执开始计算。启动等待超过 90 秒会给出提示，不会擅自判定进程已停止；排队中的工作仍可取消，缺少历史时间戳时显示未记录。运行 `node e2e/runner-queue-status.cjs /absolute/evidence/directory` 可使用真实 Electron/Chromium 控件和生产适配器验证界面，Runner 回执为模拟，不调用真实模型或远程 Hub。

关闭对话中的自动化表单后，会在消息流原位置保留草稿卡片，点击“继续编辑”即可恢复已填写内容。重新打开会话后仍保留入口和收起状态。关闭或重新编辑草稿不会创建自动化计划。

## 设备直连与会话迁移

在接收电脑打开「我的 → 登录设备 → 本人设备直连与会话迁移」，启用监听，将可直达的地址和一次性配对信息交给另一台设备，并在原生确认框核对身份。两台电脑须同时在线。在已打开的本机会话中选择「添加与设置 → 迁移到本人设备」，预览并勾选需要的文件，默认不勾选文件。接收方逐次确认。存在排队消息、待审批操作、活动目标、结果未明的工具，或目标底座不可用时，会暂停交接。交权后源机保留只读记录。回执丢失时，重连同一目标并在「迁移恢复」核对。

工作目录无法安全列出或超出上限时，可以只迁移历史。当前两台电脑直接传输正文、勾选文件和签名交权凭证。迁回曾经持有会话的电脑时，接收方用原交权记录验证整条签名链，并检查本机保留的历史有无冲突。此前经手的电脑可以离线。接收方为勾选文件创建独立工作目录。单次迁移支持 24 MiB 会话历史和最多 4,000 个文件，文件总量上限为 96 MiB。单条会话最多支持 256 次连续交权，已有签名链的总大小上限为 256 KiB。

登录或登记时签发有效期为 30 分钟的设备证书。直连使用已签发证书，过期后需重新登录。本机退出登录或切换账号会立即使直连请求失效。离线对端可能继续接受此前签发的证书，最长到证书到期。签名角色标识登记的应用设备。已配对的同账号移动端可以查看并继续所选电脑上的会话。桌面对消息 ID 持久化去重，需求追问仍须通过原需求鉴权。本仓库提供未来手机端对接所需的桌面服务和协议。可用隔离的后端 Python 运行 `node --test tests/device-peer-transport.test.cjs` 验证真实回环 TLS。常规 `npm test` 会验证长历史分页读取、Runner 交接及含真实持久化历史的设备迁移。Electron 用例 `e2e/device-direct-ui.cjs` 接受绝对证据目录，使用合成回调验证界面。

## 开发与验证

模型能力报告 v3 验证完整的流式工具往返：最后一条消息为合成的工具结果，保留工具定义，要求模型返回该结果且不强制再次调用工具。旧 v2 报告中的工具成功结论需要重新检测，独立的图片和流式证据仍保留。通过检测只证明这次小请求可用，不代表所有生产提示词或供应商策略都已验证。请同时更新桌面与 Hub，并为已有模型重新执行工具能力检测。

工具结果续答省略 `tool_choice`，与原生 Pi 请求一致。一般 403 会将该项标为尚未确认，不跳过独立检查，也不据此诊断密钥权限不足。明确的认证与计费错误仍分别处理。

Hub 模型拒绝错误通过 JSON、SSE 和原生会话摘要保留不透明的 `soduwork-trace` 编号，可用其关联 Hub 传输日志中经过校验的上游请求编号。一般 HTTP 403 表示请求被拒绝，不能据此断定密钥权限错误。已完成的工具与文件仍保留，403 不会触发自动重试。

模型临时故障共用既有的单轮重试预算。供应商的 `Retry-After` 是最短等待时间：超过剩余时间预算时停止自动重试，不缩短等待。已识别的计费或额度耗尽错误不重试。已产生的输出和工具结果继续通过既有显式恢复流程保留。

首次体验推荐根目录的 `sh start.sh --desktop`。根目录启动器在专用 `venv/` 中安装 Hub 和 Runner 依赖，并明确将生成的桌面副本绑定到同一 Python 解释器。独立开发时保持 Hub 运行，在 `client/` 安装依赖 `npm ci` 后执行 `npm start`，三种桌面系统共用这一入口；这种方式使用安装了 `requirements-runner.txt` 的 `../hub-backend/.venv`。两种方式都执行当前后端源码，不要手工复制旧发行版 Runner 代替当前源码。

`npm test` 运行客户端的单元和契约检查。`npm run check:layout` 检查源码与生成目录的边界。`e2e/` 脚本应按文件声明选择隔离夹具或真实服务：隔离界面通过不等于真实模型、用户账号或线上交付验证通过。

运行 `node e2e/plugin-authoring-intent.mjs /absolute/evidence/directory`，可在隔离 Electron 中检查已授权作者上下文、生成后的安装卡和安装确认。文件生成使用确定性夹具，不调用真实模型。将 `SODUWORK_TEST_PYTHON` 指向装有后端测试依赖的 Python 环境，再运行 `node e2e/mate-attachment-notices.cjs /absolute/evidence/directory`，可通过隔离的三账号 Hub 验证收件人预览、发送人回执及第三人访问拒绝。这些检查不会向真实同事发送消息。

Windows 上运行 `npm run test:e2e:user:isolated`，使用全新的 Electron 配置目录、注册的测试账号、本地 Hub 和模拟模型服务验证桌面用户旅程。在 `hub-backend/.venv` 安装 `hub-backend/requirements-test.txt`，或将 `SODUWORK_TEST_PYTHON` 指向已安装这些依赖的解释器。结果写入 `outputs/isolated-user-journeys/report.json`，可通过 `SODUWORK_JOURNEY_OUTPUT` 指定其他证据目录。单独验证工作窗恢复时运行 `npm run test:e2e:user:isolated -- --only=UJ-09`，脚本也会执行恢复所需的任务创建和分派。

Windows 执行服务在工具初始化前加入原生 Job Object。专用 Windows PowerShell 辅助进程持有该对象，退出时确认其中的进程全部结束，包括中间 Windows 父进程已经退出的 Git Bash 后代进程。这是生命周期清理机制，不是安全沙箱；Linux 和 macOS 继续使用现有的进程树清理。

Pi 会话从只读切换为默认或完全访问时，会按已配置的默认工具重建工具选择，并保留原会话历史。默认权限下的命令仍需审批，切回只读后会移除写入和命令工具。运行 `node --test tests/access-readonly-upgrade.test.cjs`，通过本机模拟模型服务、真实文件写入和命令执行验证生产会话链路。

模型拒绝插件草稿修复请求时，对话和队列保留安全的运行时错误，不再替换为笼统的包校验错误。已有文件与工具结果仍然保留；HTTP 403 不会触发再次自动修复。草稿上的静态包诊断单独保留。

验收摘要的隔离验证命令为 `node e2e/acceptance-summary-export.cjs /absolute/evidence/directory /path/to/test/python`。Python 环境需要后端测试依赖。该脚本验证真实原生 IPC、设备认证与保存字节，保存框选择由测试注入，不使用真实模型或生产账号。

未显式配置最大输出预算时，桌面、Hub 和 Runner 使用 16384 Token，并受已配置的上下文窗口约束。这是默认值，不是检测出的服务上限。请在“我的模型”中设置“最大输出 Token”；组织模型在“模型目录”中设置，数值应符合部署服务的实际限制。思考模型可能需要显式配置更高预算，才能完成工具调用或最终回答。上下文窗口与输出上限应分别填写，不要通过缩小真实上下文窗口来绕过输出预算错误。能力检测和连接检查使用小请求，不会测出最大输出上限。模型服务拒绝已配置输出上限时，会提示调整对应配置，不自动重试。Pi 单次响应如果达到输出上限且只有思考、尚无正文或工具调用，可在同一次提交内进行一次有上限的续接。续接保留已完成的工具结果，维持原有输出预算和思考设置，要求执行更小的下一步或给出简短答复。再次耗尽仍标为未完成，不放行排队任务；取消及权限控制继续生效。这不会提高服务端上限，也不能替代上下文压缩。

模型别名不能说明其实际思考协议。确认服务提供 GLM 5.3 或 GLM 5.3 Flash 后，可在模型编辑器的高级设置中，将“思考策略”选为“GLM 5.3（始终思考）”。预设保留模型 ID、显示名称和输出上限，并声明始终开启的 Z.ai 思考协议及合法的 low/high/max 强度。初始强度未设置或为关闭时使用 low，显式支持的强度仍可使用。可识别的真实模型名称采用相同能力默认值，不根据显示名称猜测协议。未知别名的自动模式显示为由服务决定、尚未确认；对已识别的强制思考模型，明确关闭思考的配置会在执行前被拒绝。支持范围见[模型服务官方思考文档](https://docs.bigmodel.cn/cn/guide/capabilities/thinking)。调整思考策略不代表任务已完成或验收标准已满足。

## Windows 打包

Windows 交互式安装器提供英语、简体中文、日语和韩语，默认匹配 Windows 界面语言，不支持的语言回退为英语；用户可在安装前手动选择。静默更新不显示语言选择框。安装器语言不会覆盖桌面端已保存的界面语言。macOS 和 Linux 保持各自平台的安装界面。

1. 在后端虚拟环境安装 `../hub-backend/requirements-runner-build.txt`。
2. 执行 `npm run build` 或 `npm run build-portable`。
3. 发布前按当前发布门禁验证最终安装包、升级与回滚。

两种打包入口都会执行 `prepare:runner`，从 `runner_main.py` 和 `runner.spec` 重建单文件 Runner。源码、技能和依赖清单是唯一构建输入；已有 EXE 不会跳过编译。应用打包排除测试文件，Runner 资源只选择单文件可执行程序。

Windows 原生安装输入由 `scripts/payload-sources.cjs` 按清单摘要冻结，再生成 NSIS 资源表，避免文件系统过滤层向不同构建进程暴露不同字节。源文件在清单生成后发生变化时构建立刻失败。冻结输入每目录最多 64 个文件，避免编译器对大目录反复扫描；安装与验包共用一个解包函数，保留压缩与逐文件校验，旧版本的安装兼容例外见验证器。`.runtime/installer/payload-sources/` 是可重建的中间产物，不提交仓库。原生安装及其故障注入测试共用构建目录，应顺序执行。

Windows 卸载默认保留本地应用数据。交互式向导提供可选清理：显示完整目录，用户勾选并二次确认后，仅删除当前 Windows 账户的 `%APPDATA%\SoduWork` 目录，遇到目录链接则拒绝清理。外部工作区、其他 Windows 账户、Hub 服务数据和自定义 `SODUWORK_USER_DATA` 目录不在清理范围内。静默卸载与升级保留数据；旧的 `--delete-app-data` 参数会被拒绝，不能绕过确认。

OpenCode 为可选底座，不再随客户端分发，也不会在构建时下载。Agent 管理继续识别本机安装，并提供主动安装入口。`build-light` 已退役，常规构建统一采用轻量配方。

“我的模型”中的组织服务为只读，其地址、凭据、模型清单及能力检测由 Hub 管理端维护。客户端只能编辑和测试个人自建服务与本机服务；此边界需要同时更新 Hub 和客户端。历史上挂在组织服务下的个人覆盖配置仍保留存储，但不再影响该服务的地址、凭据或模型清单；组织模型继续按现有平台额度规则使用。如需使用个人凭据，请明确添加独立的个人服务。

本机模型可搭配任意本地受管底座，包括 Pi、Qwen、OpenCode、DeepSeek Harness、Kimi 和 Codex Harness。Codex 账号型底座保留自己的模型目录。本地 Agent 默认模型加密保存，并按当前 Hub、设备和账号隔离；对话、需求执行和本机自动化使用这些选择。新建对话、会话输入框、需求安排执行及自动化表单在未选择模型或所选模型已删除时，均使用第一个可用模型。本地模型排在 Hub 模型之前，有效的已有选择保持不变。既有会话切换到替代模型继续对话时，保留原会话历史。本地模型调用不消耗 Hub 模型额度，但仍须满足正常的账号和执行权限。

在 Agent 管理中，受管底座未保存模型或原模型已删除时，会显示并测试列表中的第一个可用模型。本地模型排在 Hub 模型之前，有效的已有选择继续保留。自动回退不会改写加密保存的偏好。没有可用模型时仍显示不可用；安全存储读取失败会报错，不会被当作模型删除。运行 `node e2e/agent-single-model-default.cjs /absolute/evidence/directory` 可通过真实 Electron 界面、加密存储和私有 IPC 验证默认选择、删除回退及测试路由。该测试中的 Hub 与 Runner 回执为模拟数据，不调用真实模型服务。

本机自动化定时执行时，会先验证设备模型映射的归属，再按相同规则解析模型并创建会话。它保留自动化原来保存的偏好，只在本次执行使用替代模型。对于已保存的 Hub 模型被删除的自动化，需要同时部署客户端和 Hub 改动，由 Hub 允许原设备重新解析缺失的选择。远程目标与账号型底座保留原有准入规则。目录读取失败或不完整不代表模型已删除；本地模型可以离线使用，也不意味着可以自动替换尚未确认状态的 Hub 模型。

云端对话、远程派发和 Hub 管理的工作流不接受本地模型引用。本地 Agent 测试通过桌面的私有 Runner 管道执行，不向 Hub 发布模型配置或测试日志。Pi 可使用本地 OpenAI 兼容图片模型直接生图，成果保存在本机工作区，支持 base64 图片数据或同源成果链接；尚未提供本地视频生成功能。无法验证账号归属的旧自动化模型映射会保留在加密存储中，并要求用户重新选择模型。本地模型准入 E2E 使用真实 Electron 进程和模拟的本机服务，覆盖默认选择、删除、账号隔离与配额行为。

底座名单、显示信息、模型归属及权限声明来自 `../hub-backend/app/agent_catalog.json`，打包复制到 `resources/agent_catalog.json`；不在渲染端再维护第二份支持名单。扩展方式见 [Agent 扩展约定](../docs/release-scope.md)。
